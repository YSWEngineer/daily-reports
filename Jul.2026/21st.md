## 💡 本日の学び・気付き
### 正規化（normalization）
テーブルについて、システムでの利用がスムーズに行えるように整理する作業のこと。
特に、データの登録、変更、削除が整合的に行えるように、テーブルのフォーマットを整理することが目的。
正規化には何段階かレベルがあり、第1〜第5正規形がよく知られている。
通常の業務では第3正規形まで理解すれば十分。

### 正規形（normal form）
データベースで保持するデータの冗長性を排除し、一貫性と効率性を保つためのデータ形式のこと。

### 概念設計
管理すべき情報はどのようなものなのかを整理する。
この段階では、データベースやシステムの実装は考えず、要件に登場する情報だけをざっくりと把握する。
たとえば、家計管理データベースであれば、扱うべき情報として「利用者情報」や「入出金情報」などがあることを明確にする。
また、情報間で関連がある場合、どのような関係があるかも併せて整理する。

### 論理設計
概念設計で明らかになった各情報について、RDB を使う前提で構造を整理し、詳しく具体化していく。
論理設計では「どのようなテーブルを作り、それぞれのテーブルにどのような列を作るか」まで明らかにすれば十分。
データ型や制約などの実装に関わる内容は、この段階では考えない。

### 物理設計
特定の DBMS製品を使う前提に立ち、論理設計で明らかになった各テーブルについて、その内容を詳しく具体化していく。
すべてのテーブルのすべての列について、型、インデックス、制約、デフォルト値など、テーブル作成に必要なすべての要素を確定させる。
ちなみに、この物理設計に基づいて、CREATE TABLE文などを含む一連の DDL文を作成し、最終的にデータベース内にテーブルを作成することができる。

### DDL
DDL（Data Definition Language）はデータ定義言語のことで、CREATE、ALTER、DROPなど、データベースやテーブルの構造を定義・変更・削除するための命令を指す。

### 概念設計のイメージ化
- エンティティ：「テーブル」のようなもの。
- 属性：テーブルの「列」のようなもの。
- 関連：「リレーションシップ」のようなもの。

### ER図
概念設計の成果は、ER図（ERD：entity-relation diagram）という図にまとめることが一般的。
ER図を使うことで、エンティティ・属性・リレーションシップの関係を俯瞰して把握できる。
ER図には、2つの記述形式がある。
ジェームズ・マーチンが考案した IE（Information Engineering）という形式に基づく ER図。
アメリカ空軍が開発した IDEF1X という形式も広く使われている。

### 多重度（カーディナリティ）
エンティティ同士の数量的な関係を多重度やカーディナリティという。
たとえば、家計管理の場合は1人の「利用者」が複数の「入出金行為」をする可能性があるため、「利用者」と「入出金行為」の2つのエンティティは「1対多」の多重度があるといえる。

### 主キー（primary key）
「この値を指定することで、ある1行を完全に特定できる」という役割を担う列のこと。
主キーは次のような特性を持っている。
- 必ず何らかのデータが格納される（NULL ではない）。
- ほかの行と値が重複しない。

### 外部キー（foreign key）
他のテーブルの主キーを参照し、テーブル同士を関連付けるための列。

### エンティティを導き出す方法
#### Step1：候補となる用語を洗い出す
- 要件の中から「名詞」を抜き出す。
- 要件が実現されている姿を仮定して、そこに登場する「人」「物」「事実」「行為」などの用語を書き出す。

#### Step2：不要な用語を捨てる
- 他の用語の具体例でしかないものを捨てる。
- 計算や集計をすれば算出可能な値は捨てる。

#### Step3：関連がありそうなものをまとめる
- 同じ用語に関連するものを集める。

#### Step4：エンティティ名と属性名に分ける
- Step3 でまとめたグループの中で「〜の〜」という日本語が成り立つ場合、前者がエンティティ名に、後者がその属性名になる。

### erDiagramとは？
Mermaid というライブラリで ER図を描くための構文（書き方）。
#### Point1：ライブラリと構文は別物
- Mermaid：ダイアグラムを描画する機能を持つライブラリ。
- erDiagram：その Mermaid に対して「これから ER図を描きます」と伝える宣言。

#### Point2：基本構造
```
erDiagram
  USERS ||--o{ TRANSACTIONS : records
  USERS {
    int id PK
    string name
  }
  TRANSACTIONS {
    int id PK
    int user_id FK
    int amount
  }
```
1行目の`erDiagram`が宣言で、2行目以降が具体的な中身。
中身は大きく2種類。
1. リレーションシップの行：`USERS ||--o{ TRANSACTIONS : records`のように、2つのエンティティと、その関係を1行で表現する。
2. テーブル定義のブロック：`{}`の中にカラム名・型・主キー（PK）・外部キー（FK）を書く。
