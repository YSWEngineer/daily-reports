## 💡 本日の学び・気付き
### 11.1 まず再現手順を短くする
結論：**デバッグでは、不具合の原因を思い込みで決めつけず、実際に起きていることを確認しながら特定することが大切！**

たとえば、映画を登録したのに詳細画面が表示されなかったとする。
このとき、いきなりコードを書き直すのではなく、次のような場所を順番に確認する。
<div style="
  border: 1px solid #ccc;
  padding: 16px 24px;
  width: fit-content;
  max-width: 100%;
  margin: 16px auto;
  box-sizing: border-box;
  text-align: center;
  line-height: 1.8;
">
  <strong>映画図鑑のデバッグで確認する場所</strong><br>
① ブラウザ<br>
画面に何が表示されているか<br>
↓<br>
② HTTP通信（Networkパネル）<br>
URL・メソッド・ステータスコード・送信データ<br>
↓<br>
③ Sinatra<br>
リクエストを正しく受け取って処理したか<br>
↓<br>
④ ERB<br>
データを正しく HTML に表示しているか<br>
↓<br>
⑤ JSONファイル<br>
データが正しく保存されているか<br>
</div>

このように、問題が発生している場所を一つずつ調べていく。
FBC Press: Sinatra ではこれを「**切り分け**」と表現している。

### 11.2 ブラウザの表示と Networkパネルを分けて見る
**ブラウザに表示された画面だけで判断せず、画面の裏側で行われている HTTP通信も確認する習慣を身に付けること。**

たとえば、映画を登録したのに詳細画面が表示されなかった場合、画面だけでは、登録そのものに失敗したのか、登録には成功したけれどとダイレクトに失敗したのか、判断はできない。
そこで、 Networkパネルを活用する。

Networkパネルでは、ブラウザとサーバー間で行われた通信を確認できる。
特に覚えておきたいのは次の項目。
|項目   |何を確認するのか？   |
|---|---|
|URL   |どこにアクセスしたのか？   |
|HTTPメソッド   |GET, POST, PATCH, DELETE のうちどれなのか？   |
|ステータスコード   |処理が結果的にどうなったのか？   |
|Form Data   |フォームから何が送信されたのか？   |
|Response Headers   |サーバーがどのような情報を返したのか？   |

たとえば、登録後に詳細画面へ移動しなかった場合、次の順番で調べる（多分）。
1. `POST /movies`が送信されているのか？
2. レスポンスが`303`になっているのか？
3. `Location`が正しい`URL`を指しているのか？
4. リダイレクト後の`GET`が成功しているのか？

### 11.3 Sinatra のログを見る
Sinatra を起動するとターミナルには、Sinatra のサーバーが起動したことを示す情報や、ブラウザからアクセスするたびに追加されるログが表示される。
操作直後に追加された行を確認すると、どの操作に対するログなのかを見失いにくくなる。

### 11.4 params と JSONファイルを見る
フォームから送られたデータ届いているのかを調べるには、`params`を確認する。

#### 復習：データの流れを振り返る

<div style="
  border: 1px solid #ccc;
  padding: 16px 24px;
  width: fit-content;
  max-width: 100%;
  margin: 16px auto;
  box-sizing: border-box;
  text-align: center;
  line-height: 1.8;
">
① フォーム<br>
利用者が映画情報を入力する<br>
↓<br>
② params<br>
Sinatra が送信された値を受け取る<br>
↓<br>
③ 保存処理<br>
save_movies で JSON に書き込む<br>
↓<br>
④ data/movies.json<br>
フォームに入力した映画データが保存される<br>
</div>

#### params とは？
`params`は、フォームなどから送られてきた値を Sinatra で受け取るためのもの。
たとえば、フォームに次のような項目があるとする。
```html
<input type="text" name="title">
```
この`name="title"`が、Sinatra側で値を取り出すときのキーとなる。
```ruby
params["title"]
```

#### JSONファイルで何を確認するのか？
`data/movies.json`を確認すると、実際に保存された映画データが分かる。
画面に表示されなくても、JSON に保存されていれば、フォーム送信や保存処理ではなく、表示側に問題がある可能性がある。

### 11.5 ERB のエラーを読む
たとえば、映画一覧画面が突然表示されなくなったとする。
原因として、次のようなことが考えられる。
- ERB の書き方を間違えた。
- Ruby の変数名を間違えた。
- Ruby の処理を実行したときにエラーが発生した。

こうした問題が発生すると、HTTPステータスコードが`500`になることがある。

### 11.6 layout.erb と各ERB の役割を確認する
映画図鑑には、複数の ERBファイルが存在している。
- `layout.erb`
- `index.erb`
- `show.erb`
- `new.erb`
- `edit.erb`

これらは全て同じ役割を持っているわけではない。
**共通部分**
`layout.erb`
HTML全体の外枠や共通のヘッダーなどを担当する。

**画面ごとの内容**
各 ERBファイル
一覧・詳細・登録・編集など、それぞれの画面に固有の内容を担当する。
- `index.erb`：映画一覧
- `show.erb`：映画詳細
- `new.erb`：新規登録
- `edit.erb`：編集

|ファイル   |役割   |
|---|---|
|layout.erb   |HTML全体の外枠・共通部分   |
|index.erb   |映画一覧の内容   |
|show.erb   |映画詳細の内容   |
|new.erb   |映画登録フォーム   |
|edit.erb   |映画編集フォーム   |

映画一覧を表示するときは、`index.erb`だけで画面全体を作るのではなく、共通の外枠である`layout.erb`と組み合わせて表示する。

FBC Press: Sinatra では、次のような構造が紹介されている。
```erb
<!doctype html>
<html lang="ja">
  <head>
    ...
  </head>
  <body>
    ...
    <%= yield %>
  </body>
</html>
```
ここで重要なのが、次の部分。
```erb
<%= yield %>
```
`yield`は、**各画面の ERB の内容を差し込む場所。**
たとえば、映画一覧を表示するときは、`index.erb`の内容がこの場所に入る。

#### なぜ役割を分けるのか？
たとえば、すべての ERBファイルに次のような HTML構造を書いてしまったとする。
```html
<html>
  <body>
    <!-- 各画面の内容 -->
  </body>
</html>
```
共通部分が重複し、HTML の構造が崩れる原因になる。
また、ヘッダーや共通のレイアウトを変更するときに、複数のファイルを修正しなければいけなくなる。
そこで、`layout.erb`に共通部分をまとめ、各 ERB には画面固有の内容だけを書くようにする。
これは、**同じ内容を何度も書かず、役割ごとに整理する設計である。**

#### HTML の構造以外にも確認すること
FBC Press: Sinatra では、次の2点も確認対象として挙げられている。
**① フォームの label と入力欄が対応しているか？**
たとえば、次のような HTML。
```html
<label for="title">タイトル</label>
<input type="text" id="title" name="title">
```
`label`の`for="title"`と、入力欄の`id="title"`が対応している。

**② リンクやボタンの文言が分かりやすいか？**
「詳細を見る」「編集する」「削除する」のように、何ができるのかが文言からわかることも大切。

### 11.7 症状ごとに最初に見る場所
**問題が発生したとき、闇雲にコードを調べるのではなく、症状に応じて確認する場所を見極めることが大切。**
|症状   | 最初に見る場所  |
|---|---|
|フォームを送っても値が届かない   |Networkパネルの Form Data、フォーム部品の name   |
|登録後に増えない   |POST /movies のステータス、data/movies.json   |
|更新しても変わらない   |Networkパネルの _method=patch、Sinatra のログ（ターミナル）、JSON   |
|削除しても残る   |Networkパネルの _method=delete、Sinatra のログ（ターミナル）、JSON   |
|404 になる   |URL、映画ID、JSON内の ID   |
|500 になる   |ターミナルのエラーメッセージ、ERB の行番号   |
|画面が崩れる   |HTML構造、layout.erb と各 ERB、CSS   |
|入力したタグが動いてしまう   |hヘルパーが外れていないか？   |

### 11.8 よくある失敗を切り分ける
よくある実装ミスについて、次の3つの失敗例が紹介されている。
1. JSONファイルを`public/`に置いてしまう。
2. POST の後に直接 HTML を返してしまう。
3. Ruby の`gsub`で改行を`<br>`に変換する。

それぞれ、問題が発生する場所が異なることに注意！

### 考えてみよう
**画面だけを見て原因を決めると、どのような間違いが起きそうでしょうか。**
回答：画面に表示されていないだけで、登録や保存そのものが失敗したと決めつけてしまう可能性がある。

**JSON に保存されているのに画面に出ない場合、どこを疑えばよいでしょうか。**
回答：表示側の処理を疑う。たとえば、ルートの処理や映画ID の検索、ERB による画面表示などを確認する。

**500 が出たとき、なぜまずターミナルのエラーメッセージを見るのでしょう**か。
回答：エラーメッセージには、エラーの内容や発生したファイル名、行番号などが表示されることがあるため。それらを手掛かりに、問題が起きている場所を特定しやすくなる。
