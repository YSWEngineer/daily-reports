## 💡 本日の学び・気付き
### 「ツイートする」機能のPathを考える
まず、ユーザーが文章を入力して「ツイートする」ボタンを押したとき、何が新しく作成されるのかを考えた。
ボタンを押すことで新しいツイートが作成されるため、リソースは「**ツイートそのもの**」であると考えた。

次に、HTTPメソッドについて考えた。
今回は情報を取得するのではなく、新しいツイートを作成する操作である。
そのため、HTTPメソッドは`POST`が適切であると判断した。

続いて、Path を考えた。
最初は`/tweets/123`ではないかと考えた。
固有の ID が付くことで、ツイートを識別しやすいと考えたためである。

しかし、作成する前からツイートの ID がわかっている必要があるのか、改めて考えた。

新しいツイートは、まだ存在していないため、作成する時点では固有の ID が決まっていない。
作成後に ID が割り当てられればよいので、今回はツイートの集合を表す`/tweets`が適切であると判断した。

最後に、Description には「新しいツイートを作成する」と記述した。

「ツイートする」の設計は、以下のとおりである。
|HTTPメソッド   |Path   |Description   |
|---|---|---|
|POST   |/tweets   |新しいツイートを作成する   |

今回の学習では、リソースの集合を指定する場合と、特定のリソースを指定する場合では、Path の考え方が異なることを学んだ。

- `POST`：新しいリソースを作成する操作。
- `/tweets`：ツイートの集合を指定する Path。
- `/tweets/123`：ID が 123 の特定のツイートを指定する Path。

最初は、固有の ID を使うことで識別しやすくなる点に注目していた。
しかし、どのリソースを操作するのかという視点も重要であることが分かった。
