## 💡 本日の学び・気付き
### pjordさんのアドバイスを理解する
#### 読み込みと保存の処理の関係を理解する
##### 読み込みと保存は対になっている
[pjordさんからのコメント](https://bootcamp.fjord.jp/reports/128283#comment_217028)を受けて、JSONファイルの読み込みと保存の処理について整理した。
**① 読み込み：ファイルから Ruby のデータへ**
```
JSON.parse(File.read(MOVIES_FILE))
```
- `File.read`：ファイルの内容を文字列として読み込む。
- `JSON.parse`：JSON形式の文字列を Ruby の配列やハッシュに変換する。

つまり、**ファイル → 文字列 → Ruby の配列・ハッシュ**という流れになる。

**② 保存：Ruby のデータからファイルへ**
```
File.write(MOVIES_FILE, JSON.generate(movies))
```
- `JSON.generate`：Ruby の配列やハッシュを JSON形式の文字列に変換する。
- `File.write`：文字列をファイルに書き込む。

つまり、**Ruby の配列・ハッシュ → 文字列 → ファイル**という流れになる。

##### データがどのような形なのかを意識する
読み込みと保存では、処理の順番が反対になっている。
|処理   |メソッド   |役割   |
|---|---|---|
|読み込み   |File.read   |ファイルから文字列を読み込む   |
|読み込み   |JSON.parse   |文字列を Ruby の配列・ハッシュに変換する   |
|保存   |JSON.generate   |Ruby の配列・ハッシュを文字列に変換する   |
|保存   |File.write   |文字列をファイルに書き込む   |

##### 🤔 自分なりに考えたこと
- メソッドの名前を一つずつ覚えるだけでなく、処理の途中でデータがどのような形になっているのかを意識することが大切。
- 今後、コードを読むときも、データが「ファイル」「文字列」「Ruby の配列・ハッシュ」のどの状態なのかを考えながら、処理の流れを理解していきたい。

### 5.7 映画を追加して保存する
#### POST /movies で映画を登録する
これまでに作成した`load_movies`、movie_params`、`save_movies`を組み合わせ、フォームから送信された映画を保存する処理を実装した。

まず、`load_movies`で保存済みの映画データを読み込み、`SecureRandom.uuid`で生成した ID と、`movie_params`で取得したフォームの入力値を`merge`で結合する。

次に、`movies << movie`で新しい映画を配列に追加し、`save_movies(movies)`で配列全体を JSONファイルに保存する。

保存後は`redirect "/movies"`によって映画一覧ページへ移動し、登録した映画が一覧に表示されることを確認する。

#### 今回の学びのポイント
これまで個別に作成してきた**読み込み・ID生成・入力値の整理・保存の処理**を組み合わせることで、映画を登録する一連の流れが完成する。
また、データを保存することと、保存後に画面を表示することは別の処理であり、それぞれの役割を順番に繋げることが重要である。

### 5.8 利用者の入力を安全に表示する
#### HTMLエスケープによるセキュリティ対策
① `Rack::Utils.escape_html(value)`
- **何をする？**：HTMLエスケープを行う。
- **何のために？**：入力された文字列が意図しない HTML として解釈されるのを防ぐため。

② `h(value)`を定義すると、何が便利になるのか？
HTMLエスケープ（`Rack::Utils.escape_html(...)`）を簡単に呼び出せるようになる。

③ なぜ HTMLエスケープが必要なのか？
入力された文字列を意図しない HTML として解釈させないため。

|対象   |役割   |
|---|---|
|Rack::Utils.escape_html(value)   |HTMLエスケープを実行する   |
|h(value)   |HTMLエスケープを簡単に呼び出すためのメソッド   |
|h(movie["title"])   |映画のタイトルをエスケープしてから出力する   |

#### 今回の学びのポイント
`Rack::Utils.escape_html`が実際の変換処理を担当し、`h`はそれを簡単に呼び出すための窓口になっている、という関係。

### 5.11 この章の完成コード
#### 考えてみようについて
**質問 ①：なぜタイトルや配列の位置ではなく、UUID を ID にするのでしょうか？**
答え：映画を一意に識別し、タイトルが変わったり、配列の順番が変わったりしても、同じ映画を特定できるようにするため。

**質問 ②：なぜ保存用 JSON を public/ に置かないのでしょうか？**
答え：`public/`はブラウザから直接アクセスさせるファイルを置く場所であり、アプリケーションが管理する保存用データは別の場所に分けるため。

**質問 ③：保存後に直接 HTML を返すのではなく、なぜ別の URL へ移動させるのでしょうか？**
答え：映画の登録処理と一覧表示の処理を分け、登録後は GETリクエストで最新の一覧を取得するため。

以上の3つの問いをまとめると
|質問   |設計上の理由   |
|---|---|
|なぜ UUID を ID にするの？   |タイトルや並び順に左右されず、映画を識別するため。   |
|なぜ JSON を public/ に置かないの？   |公開用ファイルと、アプリが管理するデータを分けるため。   |
|なぜ保存後にリダイレクトするの？   |登録処理と一覧表示を分けるため。   |

### XSS（クロスサイトスクリプティング）について
**XSS（クロスサイトスクリプティング）**とは、Webサイトに悪意のあるスクリプトを埋め込み、そのサイトを閲覧した人のブラウザで実行させてしまう脆弱性のこと。

#### たとえば、どんなことが起きるの？
映画アプリに、ユーザーがタイトルや説明文を入力できる機能があるとする。
もし、入力された文字列を適切な対策なしで HTML に出力すると、悪意のあるスクリプトまでブラウザに実行されてしまう可能性がある。
その結果、状況によっては、ログイン地宇野ユーザーに関する情報を盗まれたり、ユーザーの意図しない操作につながったりする危険がある。

#### 今回の Sinatra の学習との関係
そこで学んだのが、**HTMLエスケープ**。
```erb
<%= h(movie["title"]) %>
```
このコードでは、`h`によって HTML として特別な意味を持つ文字を変換してから出力する。
たとえば、`<b>テスト</b>`という文字列をエスケープすると、ブラウザにタグそのものを文字列として表示できる。

#### 覚えておきたいこと
- **XSS**：悪意のあるスクリプトが Webサイトを通じてブラウザで実行される脆弱性。
- **HTMLエスケープ**：HTML として特別な意味を持つ文字を変換し、意図しない解釈を防ぐ対策の一つ。
