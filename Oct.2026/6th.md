### 書籍『Webを支える技術』
#### Webらしい設計とREST
- Webサービスには、簡単に接続できるものと、接続するのが難しいものがある。その違いの一つが「**Webらしい設計**」である。
- Webらしい良い設計をするためには、**Webのアーキテクチャを理解し、それを意識することが重要。**
- アーキテクチャとは、簡単にいうと**システム全体の構造・設計**のこと。
- アーキテクチャスタイルには、MVC（Model・View・Controller）、パイプ＆フィルタ、イベントシステムなどがある。
- **RESTはネットワークシステムのアーキテクチャスタイル**であり、クライアント / サーバなど、複数のアーキテクチャスタイルを組み合わせた複合アーキテクチャスタイルである。
- Webはクライアント / サーバ型のシステムであり、RESTはクライアント / サーバから派生したアーキテクチャスタイルである。
- コンポーネントとは、システムを構成する**役割を持った部品・構成要素**のこと。
- 各コンポーネントに制約を設けることで、それぞれが協調して動作できるようになる。
#### RESTの6つの制約
REST は、以下の6つを組み合わせたアーキテクチャスタイル。
1. **クライアント / サーバ**：ユーザインタフェースと処理を分離する
2. **ステートレスサーバ**：サーバ側でアプリケーション状態を持たない
3. **キャッシュ**：通信回数や通信量を減らす
4. **統一インタフェース**：インタフェースを固定する
5. **階層化システム**：システムを階層に分離する
6. **コードオンデマンド**：プログラムをクライアントにダウンロードして実行する

また、**RESTful** とは REST の制約に従っていて「RESTらしい」ことを指す。
#### リソース
- リソースとは、Web上に存在する、名前を持ったあらゆる情報のこと。
- 1つのリソースは複数の表現を持つことができる。
- Web上のリソースはURIによって識別でき、HTTPを使って操作できる。
#### URI
URI は Uniform Resource Identifier の略で、簡単にいうと、
**Web上のリソースを統一的に識別するための名前**である。

例えば、
```
http://blog.example.jp/entries/1
```
の場合、
- URIスキーム：http
- ホスト名      ：blog.example.jp
- パス               ：/entries/1

となる。
また、URIはURLとURNを総称する名前である。

##### URIを変わりにくくするためのポイント
- プログラミング言語に依存した拡張子を使わない
- 実装依存のパス名を使わない
- プログラミング言語のメソッド名を使わない
- セッションIDを含めない
- リソースを表す名詞を使う

シンプルなURIは可読性が高く、ユーザーがURIの構造を推測しやすくなるため、**ユーザビリティの向上にもつながる。**

また、Webの標準化を行っている団体として**W3C**（World Wide Web Consortium）がある。
簡単にいうと、**Webのルールや標準を作っている国際的な団体。**

#### エンコーディング
データを一定の規則（ルール）に従って、別の形式や目的に合った形に変換することを意味する。

#### HTTPとステートレス
HTTPは**ステートレスなプロトコル**である。
ステートレスとは、**サーバーがクライアントのアプリケーション状態を管理せず、リクエストを基本的に独立したものとして扱うこと**である。
一方、ステートフルでは、過去のやり取りや処理途中の状態を保持する。

##### アプリケーション状態
アプリケーション状態とは、**その時点で、アプリがどのような情報を保持しているか**ということ。

例えば、
- ログインしているユーザー
- ショッピングカートの中身
- 現在の状態
- 入力途中のフォーム内容

などがある。

##### ステートフルとステートレスの違い
ステートフルでは、「**サーバーがクライアントのこれまでの状態を覚えている**」のに対し、ステートレスでは、「**必要な情報を毎回リクエストに含めて送る**」という考え方になる。

ステートレスな通信では、リクエストの処理に必要な情報がすべて含まれている**自己記述的メッセージ**が重要になる。

##### ステートフルの問題
サーバーがクライアントの状態を保持すると、クライアント数が増えた際に状態管理が難しくなり、サーバーを複数台に増やす**スケールアウト**も難しくなる。
- アーキテクチャ：システムの構造・設計
- クライアント：サーバーにサービスを要求する側
- スケールアウト：サーバーの台数を増やして処理能力を高めること

一方、ステートレスにも、通信データ量の増加や認証などの処理を繰り返すことによるパフォーマンス低下、通信エラー時にリクエストが処理されたか判断しづらいといった欠点がある。

#### HTTPメソッド
HTTP には8種類のメソッドがある。
- **GET**：リソースの取得
- **POST**：子リソースの作成、リソースへのデータの追加、そのほかの処理
- **PUT**：リソースの更新、リソースの作成
- **DELETE**：リソースの削除
- **HEAD**：リソースのヘッダ（メタデータ）の取得
- **OPITONS**：リソースがサポートしているメソッドの取得
- **TRACE**：自分宛にリクエストメッセージを返す（ループバック）試験
- **CONNECT**：プロキシ動作のトンネル接続への変更

↑その中でも主に使うメソッドは5つか6つ。
TRACE と CONNECT はほとんど使われていない。
##### 復習：CRUD（クラッド）
HTTPメソッドのうち GET, POST, PUT, DELETE の4つは、「CRUD」という性質を満たすため、代表的なメソッドと言える。
CRUDは、Create (作成）、Read（読み込み）、Update（更新）、Delete（削除）というデータ操作の基本となる4つの処理のこと。

#### HTTPステータスコード
HTTPステータスコードは、先頭の数字によって大まかな意味を分類できる。
- 1xx：処理中
- 2xx：成功
- 3xx：リダイレクト
- 4xx：クライアント側のエラー
- 5xx：サーバー側のエラー

よく使われるものとして、

- 200 OK：リクエスト成功
- 201 Created：リソースの作成成功
- 204 No Content：レスポンスボディなし
- 301 Moved Permanently：恒久的な移動
- 303 See Other：別URIの参照
- 400 Bad Request：リクエストが不正
- 401 Unauthorized：認証が必要
- 404 Not Found：リソースが存在しない
- 500 Internal Server Error：サーバー内部エラー
- 503 Service Unavailable：サービス利用不可

などがある。

ステータスコードを分類することで、クライアントはレスポンスの詳細を知らなくても、**大まかな結果を判断できる。**これはコンポーネント同士を疎結合にするための工夫の一つでもある。

#### 冪等性と安全性
HTTPでは、通信エラーが発生した場合でも適切にリクエストを再送できるよう、冪等性や安全性という考え方がある。
- 冪等性：同じ操作を何回行っても、結果としてリソースの状態に与える影響が同じである性質。
- 安全性：操作対象のリソースの状態を変化させない性質
#### MIMEメディアタイプ・キャッシュ
MIMEメディアタイプは、HTTPでやり取りするリソースの表現形式を指定するもの。
例えば、
`text/html`
`application/json`
`image/png`
などがある。

また、**キャッシュ**とは、サーバーから取得したリソースを一時的に保存し、次回以降のアクセスで再利用する仕組み。
`Cache-Control`ヘッダを利用して、キャッシュをどのように扱うかを指定できる。
##### メタ言語
意味論において、ある言語について論じるために用いられる言語。高次言語。

#### セマンティクスとセマンティックWeb
**セマンティクス（semantics）＝意味。**
「このデータは何を意味しているのか」を明確にする考え方。
セマンティックWebは、**Web上の情報に意味を持たせ、コンピューターがその意味を扱いやすくする考え方**である。

HTMLでも、
```
<div>記事のタイトル</div>
```
より、
```
<h1>記事のタイトル</h1>
```
のように、情報の意味を表す要素を使うことで、よりセマンティックなHTMLになる。
#### JSON（ジェイソン）
JSON は JavaScript Object Notation の略で、一言でいうと、**データを構造化して表現し、コンピューター同士でやり取りするためのデータ形式**のこと。

たとえば、
```json
{
  "name": "Bowser",
  "age": 50
}
```
のように、`"キー": 値` の形式でデータを表現する。

JSONには、以下の6種類のデータ型がある。
- オブジェクト
- 配列
- 文字列
- 数値
- ブーリアン
- null

Web APIでは、JSONがデータ交換形式としてよく利用される。
#### API・Web API・REST API
**API**とは、**別のプログラムから機能やデータを利用するための窓口**のこと。
**Web API**は、**HTTPなどのWebの仕組みを使って、プログラム同士がデータや機能をやり取りするAPI**である。
そして **REST API** は、**RESTの考え方に沿って設計されたWeb API**である。
関係としては、
```
API
└── Web API
      └── REST API
```
というイメージ。

REST APIでは、**リソースを URI で表し、HTTPメソッドによって操作する。**
たとえば、
|操作   |HTTPメソッド   |例   |
|---|---|---|
|取得   |GET   |GET /users/1   |
|作成   |POST   |POST /users   |
|更新   |PUT / PATCD   |PATCH /users/1   |
|削除   |DELETE   |DELETE /users/1   |　　　　　

つまり、**「何を操作するか」は URI 表し、「どう操作するか」は HTTPメソッドで表す**という考え方。

##### Web APIとREST APIの違い
- Web API = Web を使った API全般
- REST API = REST の考え方に沿って設計された Web API
