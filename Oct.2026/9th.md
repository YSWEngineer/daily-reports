## 💡 本日の学び・気付き
### 「ユーザーを表示する」機能のPathを考える
昨日に引き続き「ユーザーを表示する」機能の Path の設計に取り組んだ。
現在、ネックになっているのは、Path をどのように設計すればよいのか分からないこと。
まず、特定のユーザーを識別するために、ID とアカウント名のどちらを使うのがよいのか考えた。

|識別方法   |メリット   |考慮する点   |
|---|---|---|
|ID   |ユーザーを識別しやすく、データベース設計との相性もよい   |ID を安定して変わらないものとして設計する必要がある   |
|アカウント名   |人が見てユーザーを識別しやすい   |アカウント名が変更される可能性がある   |

比較した結果、今回は ID を使ってユーザーを識別することにした。
何故なら、**アカウント名が変更されても、ID が変わらなければ同じユーザーを識別できる**と考えたから。
#### Pathの設計を考える
次に、ユーザーを識別するための Path を考えた。

|項目   |今回の設計   |意味   |
|---|---|---|
|HTTPメソッド   |GET   |情報を取得する   |
|Path   |/users/123   |ID が 123 の特定のユーザーを表す   |
|users   |ユーザーというリソース   |対象となるリソースの種類   |
|123   |ユーザーの ID   |対象となるユーザーを識別する情報   |

ここで、`/users/123`はデータベースのテーブルそのものではなく、 Web上で特定のユーザーというリソースを表す Path であるということ！
サーバー側では、Path から ID を取り出し、その ID を使ってデータベースからユーザー情報を取得する、という流れになる。
#### Pathから情報を取得するまでのプロセス
今回考えた処理の流れを整理すると、次のようになる。
1. ユーザーが`GET /users/123`にアクセスする。
2. サーバーが Path からユーザーID の`123`を取り出す。
3. サーバーがデータベースから該当するユーザー情報を取得する。
4. サーバーが取得したユーザー情報をレスポンスとして返す。

このように、Path は単なる文字列ではなく、**どのリソースを対象にするのかを示す役割**を持っている。
#### /usersと/users/123の違い
これも昨日大いに悩んだ箇所だったので、改めて ID を指定しない Path についても考えた。

|Path   |対象となるリソース   |想定される用途   |
|---|---|---|
|/users   |ユーザーの集合   |ユーザー一覧を取得する   |
|/users/123   |ID が 123 の特定のユーザー   |特定のユーザー情報を取得する   |

同じ`users`というリソースでも、**Path の構造によって対象が異なる**と考えた。
